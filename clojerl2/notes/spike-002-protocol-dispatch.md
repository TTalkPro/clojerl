# spike-002 协议分派基准报告(clojerl2-002)

状态:已完成。对应 [designs/03-runtime-model.md](../../designs/03-runtime-model.md) §4.2 的 spike 判据。
基准代码:[`../bench/spike-002-protocol-dispatch.escript`](../bench/spike-002-protocol-dispatch.escript)。

## 1. 判据与结论(先行)

designs/03 §4.2 定的判据:**impl 模块 + ETS 存在性缓存方案的分派吞吐只要不低于直接远程调用的 1/3,就采纳它(S2),否则退回 ETS fun 表方案(S3)。**

| 量 | 实测 | 判据 |
|---|---|---|
| S1 直接远程调用 `apply(ImplMod, Method, [X\|A])` | 1,959,973 ops/sec(510.2 ns/op) | 基准 = 1.0 |
| S2 `clj_rt_protocol:impl(P,T)` ETS 读 + `apply/3`(命中) | 1,191,964 ops/sec(839.0 ns/op) | — |
| **S2/S1** | **0.6082** | 阈值 0.3333 → **PASS(余量 1.8 倍)** |

**最终选择:采纳 designs/03 §4.1 的分派形状 —— impl 模块 + ETS 存在性缓存 + `apply/3`,不退回 ETS fun 表。**
ETS fun 表(S3)的最快形态(零环境外部 fun,663.5 ns/op)确实比 S2 快 ~21%,但它在实现上有硬约束(见 §6),而且判据本来就允许这一档差距;更重要的是它的"闭包 fun"形态(919.7 ns/op)**反而比 S2 慢**。

## 3. 场景是真的什么、模拟了什么

honest 声明 —— **被测的开销全部是真的,只有"规模"里有两处建模**:

| 组成 | 实现方式 | 真/模拟 |
|---|---|---|
| impl 模块 | 运行期用 `erl_scan` + `erl_parse` + `compile:forms` 生成 **5000 个真实 BEAM 模块** `bench_pP_tT`,每个导出 4 个 arity-2 方法 + 4 个 fun thunk,再 `code:load_binary` | **真** |
| default 模块 | 100 个真实模块 `bench_pP_default` | **真** |
| 运行时分派入口 | 真实模块 `bench_clj_rt_protocol`(`impl/2`、`impl_cold/2`、`impl_cold_nb/2`、`impl_fun/4`、`candidate/2`),即 designs/03 §4.1 那个 `clj_rt_protocol:impl/2` 的等价物 | **真** |
| impl ETS 表 | `named_table, public, set, read_concurrency`,key = `{ProtocolAtom, TypeTagAtom}`,5000 条活项 + 10000 条 `none` 负项 | **真** |
| fun ETS 表 | 两张 20000 条的表(key = `{P,T,M}`),分别存**零环境外部 fun**(`fun M:F/2`,`fun_info` 实测 `type=external, env=[]`)与**带环境闭包 fun**(捕获 `{Mod,Method}`) | **真** |
| "编译期已知 impl 模块名" | 生成模块 `bench_index:mod/2` —— 5000 分支的 `select_val`,`mod(P,T) -> bench_pP_tT`。用来模拟"模块名是调用点字面量",避免了 map/tuple 拷贝 | **建模**(用 select_val 代表字面量;对 S2/S3 用同样形状的 `bench_index:key/2`(5000 分支 select_val)生成 atom 键对,形状对等) |
| "完全直接链接"参考行 S0 | 生成模块 `bench_static:direct/5` —— 20000 分支 select_val,每个子句体是 `bench_pP_tT:mM(X,A)` 远程调用(无 apply) | **建模**(真实编译器会为每个 (P,T,M) 生成一份直接调用代码) |
| 方法体 | `m0(X,A) -> X + A + N; m1 -> X - A + N; m2 -> X + A*N; m3 -> X + A - N`(N 为该 impl 模块的常量) | **建模**(刻意做成极轻的整数运算,见 §7 caveat) |

工作负载由迭代号经乘法散列确定性派生 `(P, T, M, X, A)`,**每个策略用同一段派生代码**,散列覆盖全部 5000 个入口与 4 个方法,避免顺序扫描 ETS 造成的假性缓存命中。

## 4. 测量方法与防作弊

- 每个策略先跑一遍 300,000 次预热,再跑 3 轮,取 **best-of-3**(报告里同时打印三轮耗时,轮间抖动约 2–5%)。
- 每轮累加返回值到 checksum 并打印:命中路径上 **S0/S1/S2-hit/S3-ext/S3-clo 五行 checksum 完全相同(87015740)**,证明五条路径语义等价、没有把结果优化掉;每个策略内部三轮 checksum 也必须一致(程序会自检并打印 "reps 一致")。
- 额外一行 **H 基准:只做同样的 workload 算术、不做任何分派 = 10.0 ns/op**,即测量骨架本身的开销,只占 S1 的 2%,不会掩盖分派成本。

### 从数据里读出来的几件事

1. **`apply/3` 本身就不便宜**:S1 - S0 = 510 - 348 = **~162 ns/op**。这是任何"间接分派"方案的下界成本 —— 方案 1 之所以是上限,原因就在这里。相对完全静态直接链接,`apply/3` 要慢 ~1.47 倍。
2. **ETS 读 + `impl/2` 远程调用的增量**:S2-hit - S1 = 839 - 510 = **~329 ns/op**。从量级推测,主要不是 `ets:lookup` 的哈希本身,而是 **ETS 读必须把键和值拷出表**(每次返回一条新 list + tuple),叠加 15000 条表(约 MB 级)在 5000 个随机键上的 cache miss。这是 designs/03 §4.1 "热路径 = 一次 ETS 读 + 一次 apply" 的实测成本。(本基准没有单独隔离 `ets:lookup` 的微基准,这条归因是推断而非实测。)
3. **负缓存命中路径(276.5 ns)比命中路径(839.0 ns)还快** —— 因为未命中时落到 100 个 `Protocol__Default` 模块,代码局部性好(100 个模块 vs 5000 个)。也就是说"协议值大多落到 default"的常见场景,分派比命中还快 ~3 倍。designs 里担心的"default 路径惩罚"在 BEAM 上不存在。
4. **负缓存不是优化,是必需**:同一个"未知类型"的分派,有负缓存是 **276.5 ns**(未命中那行),没有负缓存就得每次重跑探测,是 **9,134 ns**(冷未命中·不回填那行),**差 ~33 倍**;因为 `code:ensure_loaded` 未命中本身就要 **~9 µs**(code server 往返 + code path 搜索),是一次命中分派的 ~20 倍。它按 (P,T) 只付一次,摊销到类型的整个生命周期后可以忽略 —— 但**必须缓存**,否则未命中类型每次分派都付 9 µs。
5. **S3 赢在"避开 apply",不在 ETS**。零环境外部 fun 的调用是经 fun 指针的直接调用(不分配参数 list、不走 `apply/3`),所以 663.5 ns/op 比 S2 快;但换成 designs/03 §4.2 担心的**带环境闭包 fun**,因为要 `apply` + 拷贝环境,反而变成 919.7 ns/op,**比 S2 慢 10%**。

## 6. 判据判定与最终建议

判据(designs/03 §4.2):S2 吞吐 ≥ S1 的 1/3。

- S2/S1 = **0.608**(阈值 0.3333)→ **PASS,余量 1.8 倍**;两次独立运行 0.608 / 0.618,不会被机器噪声推翻。
- **采纳 designs/03 §4.1 的分派形状**:`clj_rt_protocol:impl('Protocol', TypeTag)` 查 ETS → `{ok, ImplMod}` → `apply(ImplMod, Method, [X|Args])`,未命中 → `Protocol__Default`,并**必须保留负缓存**(§5.4)。
- **不退回 ETS fun 表**,理由(除判据本身已通过外):
  1. S3 的优势只在"零环境外部 fun"这一种形态下存在,而它要求 impl 模块额外导出一组 fun thunk;**闭包形态比 S2 还慢**。
  2. fun 存进 ETS 让表项与**具体代码版本**绑定:extend 或热升级时必须重写表项,失去 BEAM 的"旧代码继续跑旧函数"的天然语义 —— 这正是 designs/03 §4.2 记的否决理由,本基准没有推翻它。
  3. `satisfies?` / 存在性探测在 S2 下就是一次 ETS 读;在 S3 下得多维护一张"哪些 key 有 fun"的表。
  4. 0.608 的吞吐比(约 1.64 倍开销)对协议分派这个层级是可接受的:分派只发生一次,方法体本身的工作量通常远大于 330 ns。

### 固化的实现要点(交 designs/03 §4 后续落地)

- ETS 表:一张 `public + named + set + read_concurrency` 的 impl 表,key = `{ProtocolAtom, TypeTagAtom}`,value = impl 模块 atom,**或哨兵 `none` 表示负缓存**。
- `impl/2` 命中路径:一次 `ets:lookup` + `case`;命中 `none` 直接 `error`(不回表)。
- 未命中路径:拼出 `Protocol__Type` 模块名 → `code:ensure_loaded` → 成功回填模块名、失败回填 `none`。**这个路径约 9 µs,只允许每个 (P,T) 走一次。**
- 建议把 `Protocol__Type` 模块名在 extend 时以字面量形式写进回填逻辑(或用 binary),避免每次冷路径做 `list_to_atom` 字符串拼接。

## 7. 诚实的 caveat

1. **单进程单核测量**:不测多进程/多调度器下 ETS `read_concurrency` 的争用。跨进程读时,S2 的 value 是一个 atom(拷贝 1 个字),S3 的 value 是闭包 fun(拷贝 env)—— S3 在这一点上劣势只会更大,不会更小。
2. **模块名 / 键的物化是建模的**:真实运行时 `TypeTag` 已经在值的 tag 槽里(零成本),`ImplMod` 在方案 1 里是调用点字面量(零成本)。本基准用同形状的 `select_val`(`mod/2`、`key/2`)代表这两步,它们对 S1/S2/S3 是**同量级同形状**的,对 510/839/663 ns 的量级不构成主导。
3. **冷路径两行为保证"每次迭代都是真未命中"多付了一次 `ets:delete`**(约 0.1–0.2 µs),并且 `candidate/2` 里做了 `list_to_atom` 字符串拼接。这两点都让冷路径数字偏保守,不影响任何判定(冷路径只用于论证"负缓存必需")。
4. **方法体是极轻的整数运算**,所以分派开销在总耗时里的占比被放大到接近真实上限。真实协议方法体更复杂时,分派开销的**绝对值不变、占比下降** —— 也就是说真实程序里这套分派比本表显示的还要划算。
5. **绝对值不可跨机器比较**:5000 个真实模块 + 3 张 ETS 表(i-cache/d-cache 压力)对具体 CPU 敏感。可迁移的只有比值;本判据本身就是比值判据。
6. 冷路径两行的迭代数按 1/10、1/30 缩减(单次 9.8 µs × 3,000,000 需要近 10 小时),已在结果表的 iters 列标出。
7. 本基准只覆盖 designs/03 §4.2 的**分派侧**判据;**extend 侧成本(编译/加载一个 `Protocol__Type` 模块)未测** —— §4.2 的取舍表里两个候选方案的 extend 成本同为 O(本类型方法数),不影响本次判定。
